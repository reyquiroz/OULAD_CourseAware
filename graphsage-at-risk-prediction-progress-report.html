GraphSAGE for At-Risk Student Prediction

Dissertation Progress Report — Pipeline Corrections & Cross-Dataset Validation
Primary dataset: OULAD (Open University Learning Analytics) External dataset: KU Leuven Zenodo (Tiukhova et al., 2024) Pipeline version: v2_corrected Prediction window: Week 8 (56 days) Model: EnrollmentGNN (GraphSAGE heterogeneous) Evaluation: Random-student split + LCPO (22 / 6 folds)
A

What Have I Done?

This body of work covers eight structured sub-tasks that (1) identified and corrected bugs in the original GNN pipeline, (2) ran fully reproducible experiments, and (3) validated the approach on an independent external dataset.

1 — Seed Independence Fix (gnn_model.py)

Two hard-coded torch.manual_seed(SEED) / np.random.seed(SEED) calls inside EnrollmentGNN.__init__ and run_training_loop unconditionally reset the random state to the same global seed before every model is built or trained. This meant that all five model seeds (42, 123, 7, 17, 99) produced identical weight initialisations and therefore identical results — making the multi-seed design meaningless. Both calls were removed. The caller-side seed setup in run_gnn_experiment.py was already correct and now takes effect.

Impact: All original LCPO results (2 of 22 folds, all 5 seeds per fold identical) were discarded. The full 22-fold × 5-seed experiment was re-run from scratch under pipeline_version = "v2_corrected".

2 — Ablation Flag: use_interacted_with_attrs

The supervisor asked whether the interacted_with edge attribute vector (total clicks, active days, first/last day, etc.) contributes beyond graph topology alone. A use_interacted_with_attrs flag was added to EnrollmentGNN, and a new "with_iw_attrs" condition was added to the ablation study. When this flag is enabled, the model uses the full 5-dimensional edge attribute vector for each student–VLE interaction edge.

3 — Design Decisions Documentation

Four correctness decisions were documented in docs/DESIGN_DECISIONS.md with line-level code evidence:

  • Training-only normalisation: mean/std computed from training edges only, applied to full graph — prevents test-distribution leakage into feature scaling.
  • Inductive evaluation: build_train_subgraph() removes all test enrollment edges during training forward passes — GNN cannot aggregate over test students.
  • LightGBM feature & split matching: identical split functions, seeds, temporal guard (Strategy B dual guard), and LCPO fold CSVs ensure a fair GNN vs LightGBM comparison.
  • Zenodo divergences: four schema-specific adaptations documented (single temporal guard, course-section normalisation, constant student features, datetime→day-offset conversion).

4–5 — Full Experiments & Figure Regeneration

After the seed fix, all experiments were re-run and all outputs regenerated:

  • lcpo_results.csv — 110 rows: 22 folds × 5 seeds
  • random_student_results.csv — 10 rows: 5 seeds × 2 loss weightings
  • ablation_results.csv — 35 rows: 7 conditions × 5 seeds
  • 6 report figures and 4 LaTeX-ready tables regenerated via generate_report_figures.py
  • Old v1 results archived as *_v1_buggy.csv for audit trail

6–7 — Zenodo External Dataset Pipeline

A full feasibility assessment was performed on the KU Leuven Zenodo dataset (record 17087849) by direct data inspection. A CONDITIONAL GO verdict was issued with four documented schema gaps. The complete pipeline was then built:

  • src/zenodo_data.py — data loader mirroring oulad_data.py's public API
  • src/run_zenodo_pipeline.py — end-to-end pipeline (graph build → artefacts → splits → GNN → LightGBM)
  • src/run_zenodo_lgbm_only.py — PyTorch-free LightGBM runner (OOM mitigation)
  • Graph artefacts in results/zenodo/artifacts/; results in results/zenodo/
  • Cross-dataset figure: fig_cross_dataset.png

Four fully executed Jupyter notebooks committed with outputs:

GNN > LightGBM on both splits. The weighted GNN achieves a +7.2 pp AUROC advantage over LightGBM on the random-student split and a +1.3 pp advantage on LCPO. Notably, the GNN's advantage is larger under random-student evaluation, where it has seen representatives of most students during training. Under LCPO — where an entire course-presentation is held out — the advantage narrows, suggesting the GNN relies partly on student-level patterns that do not transfer across unseen courses.

The GNN's balanced accuracy advantage (+10.1 pp, random) is substantial, indicating it better calibrates predictions across both at-risk and successful student classes compared to LightGBM's recall-heavy profile (recall 0.862 vs F1 0.723).

C

What Problems Have I Encountered?

C1 — Invalid Original Results (Seed Bug)

Problem: The original LCPO results CSV contained only 2 of 22 folds, and all 5 model seeds per fold produced identical AUROC values. This was caused by two hard-coded torch.manual_seed(SEED) calls inside the model constructor and training loop that reset the random state to the same global constant on every invocation, regardless of which seed the caller had set.

Resolution: Both calls were removed from gnn_model.py. All results were discarded and re-generated from scratch. The old outputs were archived as *_v1_buggy.csv.

C2 — Out-of-Memory Segfaults on Zenodo Pipeline

Problem: Running the full Zenodo pipeline as a single Python process caused repeated segmentation faults (exit code 139). The Zenodo log files total ~675 MB uncompressed; combined with PyTorch/PyG (~500 MB), loading all data simultaneously exhausted available RAM. This occurred even after fixing the graph-build stage to stream one year at a time, because the module-level import torch in run_zenodo_pipeline.py means PyTorch is resident whenever any function from that module is imported.

Resolution: Two fixes were applied:

  1. Streaming fix: each year's log DataFrame is deleted with del log_df; gc.collect() immediately after processing, before the next year loads.
  2. Process isolation: LightGBM evaluation was extracted into run_zenodo_lgbm_only.py — a PyTorch-free script. The main pipeline delegates to it via subprocess.run(), ensuring LightGBM and PyTorch never coexist in the same process.

C3 — Zenodo Course-Section Name Mismatch

Problem: The 2021 Global economics cohort is recorded as two sections ("Global economics 1", "Global economics 2") in the course_participation table, but as the base name "Global economics" in course_content and log_activity. This caused 676 of 4,292 enrollment rows (15.7%) to fail their node lookup, producing no enrolled_in edges for those students. The LCPO folds for these sections initially produced all-skip results (single class in test set).

Resolution: A regex normalisation (str.replace(r"\s+\d+$", "", regex=True)) was applied to student_info["code_module"] in build_oulad_compatible_tables(), matching the normalisation already applied to vle and courses tables. Twelve students enrolled in both sections had identical target values; drop_duplicates on the enrollment key safely retained one row per student.

C4 — Missing enrollment_idx Attribute on Zenodo Graph

Problem: The build_train_subgraph() function in gnn_model.py requires an .enrollment_idx attribute on enrolled_in edges to track the mapping between edge position and label row. This attribute is set in the OULAD GraphDataLoader but was not set by the Zenodo-specific _build_zenodo_hetero_data() function, causing an AttributeError on the first GNN training call.

Resolution: Added data["student", "enrolled_in", "course_presentation"].enrollment_idx = torch.arange(len(ei)) to _build_zenodo_hetero_data(). Since the Zenodo enrolled_in edges are built from the deduplicated enrollment table in order, a simple arange is the correct mapping.

C5 — LCPO Type Mismatch (str vs int for presentation year)

Problem: The Zenodo enrollment DataFrame stores code_presentation as a string (e.g. "1819"), but the LCPO folds CSV stores held_out_presentation as an integer after a CSV round-trip (e.g. 1819). The comparison enroll["code_presentation"] == 1819 is always False, so every fold's test mask was empty — causing all 6 LCPO folds to skip with "single class in test set."

Resolution: Added an explicit str(ho_pres) cast when constructing the fold mask in run_zenodo_lcpo().

C6 — Merge Deduplication (4,292 vs 4,280 rows)

Problem: build_features_zenodo() returns 4,292 rows (12 duplicate enrollment keys from the Global economics 1/2 split) while the enrollment artefact has 4,280 rows. A left-join from the 4,280-row enrollment table onto the 4,292-row features table caused row multiplication, producing an IndexError when the resulting 4,292-row feature matrix was indexed with a 4,280-element boolean mask.

Resolution: Applied drop_duplicates(["id_student", "code_module", "code_presentation"]) on the features DataFrame before the merge in both run_zenodo_lgbm and run_zenodo_lgbm_only.py.

C7 — Zenodo GNN Near-Random LCPO Performance

Concern (not a bug): The Zenodo GNN achieves LCPO AUROC of 0.499 ± 0.029, and 3 of 6 folds produce F1 = 0.0 (model predicts all students as one class). This is not a pipeline error — LightGBM on the same data also declines substantially under LCPO (0.646 → 0.607). The GNN's greater sensitivity to dataset size and feature richness means it collapses to majority-class prediction on unseen course-presentations when trained on only 3,604 enrollments with VLE features alone. Assessment edges (the single largest contributor to OULAD GNN performance) are completely absent.

This is reported as a finding rather than a fix. It motivates a dissertation conclusion that the GNN's advantage over LightGBM is conditional on dataset scale and feature richness, and may not hold for small, feature-sparse datasets.
