GraphSAGE Current State Report

OULAD At-Risk Student Prediction — Week 8 Prediction Window — Prepared June 2026

Framing note. A two-layer GraphSAGE model is an appropriate starting point and is not necessarily too simple. The priority before any architectural upgrade is to ensure that the data flow, training procedure, and evaluation protocol are sound. This report documents what has been implemented, what the current results look like, and what remains to be validated.

1. Graph Construction

The heterogeneous graph is built from the OULAD relational tables through a seven-stage pipeline (src/graph_pipeline.py). Artifacts are materialized as Parquet files for weeks 2, 4, 6, and 8. All temporal filtering uses a dual-guard strategy to prevent leakage: VLE interactions and assessment submissions must both have a due date and a submission date on or before the prediction window cutoff.

2. Model Architecture

Class: EnrollmentGNN in src/gnn_model.py. The prediction unit is the enrolled_in edge: one probability per enrollment (32,593 total), so students with multiple enrollments receive independent predictions without label ambiguity.

Layer structure

ComponentDetail
Conv layer 1HeteroConv wrapping one SAGEConv (mean aggregation) per edge type; heterogeneous input dims → hidden_dim = 64. Bidirectional: forward + reverse edge types for all five relation types.
Enrollment projectionenrollment_attr_proj — nn.Linear(n_enrolled_in_attr, 64). After conv1, the enrolled_in edge attributes are projected to 64-d, scatter-mean'd to student node positions, and added to the layer-1 student representations. This injects enrollment context (age band, prior attempts, studied credits) before the second SAGEConv layer.
Conv layer 2HeteroConv, same edge types; hidden_dim → hidden_dim = 64.
Prediction headMLP: Linear(128 → 64) → ReLU → Linear(64 → 1). Input is the concatenation of the student embedding and course_presentation embedding for each enrolled_in edge.

3. Evaluation Protocols

Random-student split

Students are grouped and assigned to train (70%), validation (10%), or test (20%) without student overlap across splits. The split is fixed by seed and stored as week08_random_split.parquet. Both GNN and LightGBM read from this shared file, ensuring identical train/test populations.

Leave-Course-Presentation-Out (LCPO)

One fold per unique (code_module, code_presentation) — 22 folds total. The held-out course-presentation's enrollments form the test set; all other enrollments form training data. The validation set is drawn by sampling 10% of unique student IDs from the training pool (student-grouped, not enrollment-indexed), so no student straddles train and validation. Currently only 2 of 22 folds have been run (quick-mode validation); full results are pending.

LCPO graph masking

During LCPO training, a deep copy of the graph is modified: contains_assess and has_resource edges from the held-out course_presentation node are removed, and submitted / interacted_with edges are filtered by destination node (assessment or VLE resource belonging to the held-out CP). This preserves cross-course behavioral signal for students who are also enrolled in other courses — a correction from the earlier student-index-based filter that over-stripped training data.

7. Outstanding Issues Before Full LCPO Run

  1. Early convergence in LCPO (epoch 4). Both completed folds stop at epoch 4, which is unusually early. Possible causes: the 10% student-grouped validation set for a small course (AAA, ~380 test enrollments) may have too few at-risk examples to produce a stable AUROC signal; the learning rate or patience may need adjustment for the LCPO regime. This should be diagnosed — e.g., by running with a longer patience (50) and inspecting the loss curve — before all 22 folds are run.
  2. Submitted and interacted_with edge attributes not yet projected. The most direct improvement still available within the two-layer architecture is to apply the same enrollment_attr_proj pattern to the submitted and interacted_with edge attributes. These carry the richest behavioral signals (assessment scores, click counts) and should be injected before conv2.
  3. LCPO GNN recall is very low (18%). With F1 = 0.28 and precision = 0.56–0.77, the model achieves high precision but misses most at-risk students in the held-out course. This is consistent with the threshold being optimized on the in-distribution validation set and not transferring well to the out-of-distribution test course. Threshold recalibration or a held-out-course-specific threshold may be needed.
  4. GNN LCPO vs. LightGBM LCPO gap. On the two available AAA folds, LightGBM AUROC is ~0.76 vs. GNN ~0.74. The gap is modest on AUROC but large on F1 (0.58 vs. 0.28). This is primarily the recall problem from point 3 and not necessarily a model capacity issue.

8. Why Two Layers Are Appropriate

The two-layer design is appropriate for the following reasons:

  • Receptive field is sufficient. A two-hop neighborhood from a student node reaches: (1) their enrolled course presentations, (2) the assessments and VLE resources in those courses, and (3) other students enrolled in those same courses. This covers all the cross-student and cross-course signal available in the graph without risk of over-smoothing.
  • Representational capacity is not the bottleneck. The model achieves 0.847 AUROC on the random split with a 64-dimensional hidden layer and two conv layers — matching LightGBM. This indicates the architecture is expressive enough for the in-distribution task. Remaining gaps are in data flow (submitted/interacted_with edge attrs unused), evaluation (early stopping in LCPO), and generalization (threshold transfer).
  • The current data flow is not yet fully validated. Introducing GAT, R-GCN, or a graph transformer before confirming that (a) all behavioral features are consumed, (b) LCPO converges properly, and (c) the threshold transfers across courses would make it impossible to attribute any improvement to the model architecture rather than the data and protocol fixes.
  • Variance across seeds is already low. The GNN random-split standard deviation is ±0.004 AUROC across three seeds, indicating stable training. This is a prerequisite for meaningful architecture comparisons.
